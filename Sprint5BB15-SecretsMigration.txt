DECISAO REGISTRADA — LIMITACAO CONHECIDA ACEITA
--------------------------------------------------------------------------------

  A validacao da nova Access Key (`hub-portal-prod-runtime`) confirmou:
    Autenticacao: OK | Bucket: hub-portal-prod (nome correto) | Bucket
    vazio: OK | PutObject: OK | GetObject: OK | DeleteObject: HTTP 204
    (SUCESSO — nao retornou AccessDenied como o plano original da
    Sprint 5B-B1.3 previa).

  Causa, per relato do usuario: o console da Tigris, no momento desta
  Sprint, so' oferece o papel "Editor" para a bucket role — nao existe
  hoje uma opcao granular que conceda Put/Get/List e negue Delete
  especificamente. Isso NAO e' uma falha do Portal HUB nem do hub-sdk
  (ambos continuam sem chamar DeleteObject em nenhum caminho de codigo,
  confirmado na Sprint 5B-B1.3) — e' uma limitacao da oferta atual de
  papeis da plataforma Tigris.

  DECISAO DO USUARIO (registrada aqui para rastreabilidade): tratar como
  limitacao conhecida e aceita, e prosseguir com a migracao. O ganho de
  isolamento (bucket dedicado ao hub-portal, nao mais compartilhado com
  o bucket de validacao do hub-sdk) e' obtido integralmente; o ganho de
  segregacao de credencial de delecao (ADR-010, Modelo IAM) NAO e'
  obtido nesta migracao — fica como risco residual aceito (ver
  Sprint5BB15-GoNoGo.txt, resposta 3).

ATIVIDADE 2 — SECRETS QUE PRECISAM SER ALTERADOS
--------------------------------------------------------------------------------

  OBRIGATORIOS:

    S3_BUCKET             -> hub-portal-prod
    S3_ACCESS_KEY_ID       -> Access Key ID de `hub-portal-prod-runtime`
    S3_SECRET_ACCESS_KEY   -> Secret Access Key de
                              `hub-portal-prod-runtime`

  CONDICIONAIS (alterar SOMENTE se o console da Tigris mostrou um valor
  diferente do bucket anterior ao criar `hub-portal-prod`):

    S3_ENDPOINT   -> valor atual: https://t3.storage.dev (mantido, salvo
                     confirmacao em contrario)
    S3_REGION     -> valor atual: auto (mantido, salvo confirmacao em
                     contrario)

  NAO TOCADOS por esta Sprint (fora de escopo, ja documentado em Sprints
  anteriores):
    BUCKET_NAME/AWS_* (mecanismo legado, permanece ausente/desativado)
    BACKUP_ENGINE (Shadow Mode permanece indefinido/dormente)

--------------------------------------------------------------------------------
COMANDO EXATO (executar APENAS pelo usuario, que possui os valores reais
— eu nao recebi nem vou receber a Access Key/Secret Key por decisao
explicita sua)
--------------------------------------------------------------------------------

  flyctl secrets set `
    S3_BUCKET=hub-portal-prod `
    S3_ACCESS_KEY_ID="<ACCESS_KEY_ID_de_hub-portal-prod-runtime>" `
    S3_SECRET_ACCESS_KEY="<SECRET_ACCESS_KEY_de_hub-portal-prod-runtime>" `
    -a hub-granmarquise

  (PowerShell: o acento grave ` no final de cada linha continua o
  comando na proxima — ou cole tudo numa unica linha, sem quebras.)

  Se S3_ENDPOINT/S3_REGION precisarem mudar, adicione-os ao MESMO
  comando (nao rode um `secrets set` separado — cada `secrets set`
  reinicia a maquina; agrupar tudo num comando so' garante 1 restart em
  vez de varios):

    flyctl secrets set `
      S3_BUCKET=hub-portal-prod `
      S3_ACCESS_KEY_ID="<...>" `
      S3_SECRET_ACCESS_KEY="<...>" `
      S3_ENDPOINT="<novo endpoint, se diferente>" `
      S3_REGION="<nova regiao, se diferente>" `
      -a hub-granmarquise

  Apos rodar, aguardar o restart:
    flyctl status -a hub-granmarquise

  CONFIRMACAO SEM EXPOR VALOR (rodar depois, cole a saida aqui se
  quiser que eu prossiga com a validacao pos-migracao):
    flyctl secrets list -a hub-granmarquise
    (o DIGEST de S3_BUCKET/S3_ACCESS_KEY_ID/S3_SECRET_ACCESS_KEY deve
    ter mudado em relacao ao valor observado nas Sprints 5B-B1.1/1.2 —
    isso, por si so', ja' e' evidencia de que o comando teve efeito, sem
    nunca expor o valor em si.)

ATIVIDADE 3 — ORIENTACAO PARA O ARQUIVO .env LOCAL
--------------------------------------------------------------------------------

  Nao existe hoje um arquivo `.env` nem `.env.example` no hub-portal
  (confirmado por leitura direta do diretorio) — `.env` esta' listado no
  `.gitignore`, ou seja, e' esperado que cada pessoa mantenha o seu
  proprio, localmente, nunca commitado.

  Se voce (ou outra pessoa do time) mantem um `.env` local para rodar o
  hub-portal fora do Fly (desenvolvimento/teste manual — o mesmo uso que
  o README do `@hub/storage-client` descreve: "`.env` local para
  validacao manual"), as linhas equivalentes as' que devem ser
  atualizadas sao:

    S3_BUCKET=hub-portal-prod
    S3_ACCESS_KEY_ID=<ACCESS_KEY_ID_de_hub-portal-prod-runtime>
    S3_SECRET_ACCESS_KEY=<SECRET_ACCESS_KEY_de_hub-portal-prod-runtime>
    S3_ENDPOINT=https://t3.storage.dev
    S3_REGION=auto

  Nao criei nem alterei nenhum arquivo `.env` real neste repositorio —
  isso exigiria a credencial em texto puro num arquivo local, decisao
  que cabe exclusivamente a voce. Esta secao e' apenas orientacao.
